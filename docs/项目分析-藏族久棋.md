## 1. 项目定位

当前仓库中的主项目名为“久棋”或 `JQ`，从界面标题、解决方案命名和代码结构来看，这是一个面向本地 Windows 桌面的棋类程序。结合用户说明，可将其视为“藏族久棋”项目的当前实现版本。

这个项目不是 Web 应用，也不是服务端系统，而是一个典型的本地对弈程序，特点是：

- 前端是 `C# WinForms` 图形界面。
- 核心 AI 是 `C++ DLL` 动态库。
- AI 通过 `P/Invoke` 被 C# 层调用。
- 当前代码主流程已经覆盖“布局阶段”“行棋阶段”和“飞子基础规则”，但阵型系统与完整传统胜负体系尚未落地。

需要补充的是：依据最新规则 PDF，正式比赛规则不仅包含三阶段流程，还包含成阵型吃、吉祥阵型、传统固定棋形胜负判定，以及竞技化补充规则；当前程序已覆盖飞子基础流程和部分竞技化规则，但还没有覆盖阵型与完整传统胜负层面。

## 4. 主程序架构

主程序入口很简单，直接启动 `Form_Main`。整个前端基本可以理解为两层：

- `Form_Main`
  - 负责按钮、模式、超时、搜索深度、文件加载等流程控制。
- `MyPanel`
  - 负责棋盘状态保存、鼠标交互、局面渲染、走子确认、AI 调度。

辅助数据结构有两个：

- `APiece`
  - 表示一个棋子，保存坐标和棋值。
- `Move`
  - 表示一步棋，保存移动路径和被吃掉的棋子集合。

核心棋盘数据是 `int[14,14]` 数组。程序把“棋盘上的内容”和“落子先后编号”合并在一个数组中表达：

- `0` 表示空位。
- 正数表示该位置已有棋子。
- 奇偶性被用于区分棋子颜色。
- 数值大小还带有落子顺序信息，因此可以支持“显示落子编号”。

## 5. 业务流程与状态机

### 5.1 当前实现为三阶段基础主流程

项目最关键的设计是把对局拆成布局、走子和飞子基础能力三个层次：

- `iState == 1`
  - 布局阶段，只允许往空位下子。
- `iState == 2`
  - 行棋阶段，开始移动棋子、跳吃、成方吃子。
- `iState == 3`
  - 成方后的补充吃子阶段，等待玩家手工选择需要移除的对方棋子。

这说明当前程序建模的不是单阶段落子棋，而是“先布子，再走子，并在少子条件下允许飞子”的复合规则棋种。
需要特别指出的是：代码中的 `iState == 3` 仍只是“成方后的补吃子状态”，并不是飞子阶段本身；飞子能力由当前行动方棋子数是否 `<= 14` 动态判断。

### 5.2 布局阶段

布局阶段的规则特征从代码里可以直接看出来：

- 棋盘大小固定为 `14 x 14`。
- 当布局总数达到 `196` 时，说明棋盘被填满。
- 这与最新规则 PDF 中“正式比赛双方各需 98 枚棋子”的口径一致。
- 随后程序会把中心两个点 `(6,6)` 和 `(7,7)` 清空。
- 清空后自动切换到行棋阶段。

另外，前两手布局存在特殊限制：代码显式禁止在最开始两手就落在两个中心点上。

### 5.3 行棋阶段

行棋阶段支持两类移动：

- 走一步到相邻空位。
- 跳过对方棋子落到空位，并把中间棋子吃掉。

用户在界面中落子时，程序会：

- 先选中己方棋子。
- 计算所有可能的下一跳或下一步位置。
- 用绿色圆点高亮候选落点。
- 将临时走法保存在 `tempMove` 中。

如果是连续跳吃，`tempMove.Path` 会记录整条路径，`tempMove.Dead` 会记录所有中途被吃的棋子。

### 5.4 成方判定

行棋结束后，程序会调用 `ChengFangCount()` 检查是否成方。

这里的“成方”指的是：最后落点与同色棋子组成一个 `1x1` 正方形。代码通过检查目标点周围四个对角方向来判断是否形成方块。

如果形成一个或多个正方形：

- `needKillCount` 记录本次需要补吃的数量。
- 状态切换到 `iState == 3`。
- 玩家再手工点击对方棋子进行移除。
- 数量满足后才真正确认这一步棋。

这说明“成方吃子”是当前规则体系里的核心机制之一。

### 5.5 悔棋机制

悔棋同时覆盖两种情况：

- 布局阶段撤销最近一次下子。
- 行棋阶段撤销最近一次完整移动，并恢复被吃棋子。

在“布局刚结束、中心点刚被清空、但还没开始正式行棋”这个边界状态下，代码还专门做了回退处理，会把两个中心点恢复，然后重新回到布局阶段。

### 5.6 当前尚未落地的规则层内容

结合 [藏久棋规则整理.md](/C:/Users/林/Desktop/实验文档/论文1/work/docs/藏久棋规则整理.md) 与现有代码，可以明确当前项目尚未完整实现以下内容：

## 6. 对局模式与界面能力

界面层提供了四种模式：

- 人人对战
- 人机对战

同时提供以下控制能力：

## 7. AI 调用链路

### 7.1 C# 到 C++ 的接口方式

`MyPanel` 通过 `DllImport` 调用 AI DLL：

- `jqai.dll`

导出的主要函数有两个：

- `getAIMove`
- `destroy_hashtable`

历史版本曾在机机模式中使用 `jqai2.dll` 作为第二个 AI。2026-04-21 后，两个入口都指向已升级的 `jqai.dll`，避免机机模式一侧仍使用旧规则 DLL。

### 7.2 传参方式

界面层会把 `14 x 14` 的棋盘压平成长度 `196` 的 `byte[]`，再传给 DLL。这里存在一次编码转换：

- C# 层棋盘使用落子编号和奇偶性表达颜色。
- DLL 层只需要 `0/1/2` 这种纯状态编码。

AI 返回值不是结构体，而是一个字符串：

- 布局阶段返回单个坐标，例如 `A7`
- 行棋阶段返回整条路径，例如 `A1,A3,C3`
- 如果存在跳吃，会附带 `TC-...`
- 如果存在成方吃子，会附带 `FC-...`

这说明 UI 与 AI 的耦合点并不在共享对象模型上，而是在一套字符串协议上。

## 8. AI 引擎实现特征

结合 `ai.cpp` 源码与现有文档，可以确认 AI 不是简单的启发式落点器，而是一个相对完整的搜索引擎。

### 8.1 双搜索系统

AI 对两个阶段使用了不同的搜索入口：

- 布局阶段：`neg_alpha_beta_embattle`
- 行棋阶段：`neg_alpha_beta`

也就是说，布局与行棋并不是一个统一评估函数上切规则，而是两套近乎独立的搜索逻辑。

### 8.2 预计算表

`ai.cpp` 中内置了大规模静态预计算表，至少包括：

- 相邻连子表
- 成方关系表

这类表的作用是把运行时判断转成查表，从而降低搜索过程中的重复计算。

`JQ/test/Program.cs` 也说明仓库里保留了这类辅助生成程序，它会把某些局部邻接信息写入文件，明显服务于底层表构建。

### 8.3 哈希与置换表

AI 使用了典型的国际象棋/博弈搜索思路：

- `Zobrist Hash`
- `ProbeHash`
- `RecordHash`
- `Alpha-Beta` 剪枝
- 迭代加深

置换表大小定义为：

- `HASHTABLESIZE = 1024 * 1024 * 128`

这说明作者非常重视搜索过程中的重复状态复用，项目具备明显的“自研博弈 AI”特征。

### 8.4 评估策略

从宏定义和函数命名能确认出布局阶段与行棋/飞子阶段的主要评估方向。

布局阶段重视：

- 两连
- 三连单侧开放
- 成方
- 六方
- 准成方
- 开放度
- 对手相关惩罚

行棋阶段重视：

- 成方走法
- 跳吃走法
- 破坏对手准成方
- 棋子机动性
- 连子关系
- 大连

这说明 AI 不是只追求即时吃子，而是把“成方”和“阵型构建”当作长期战略目标。

### 8.5 结果兜底逻辑

如果搜索没有拿到理想结果，`getAIMove` 末尾还有一套兜底走法生成：

- 优先找可跳吃走法。
- 再退化到普通相邻移动。

因此从代码设计看，作者希望 AI 在极端情况下也尽量返回合法结果，而不是直接空返回。

### 9.2 主要工程风险

当前项目也有明显的历史包袱和维护风险。

#### 线程与 UI 安全

- 主窗体直接关闭了跨线程访问检查。
- AI 线程使用 `Thread.Abort()` 强制终止。
- 停止 AI 时使用忙等 `while(thread.IsAlive){}`。

这类写法在旧式桌面程序里常见，但稳定性一般，容易带来：

- UI 卡死
- 状态未完全回收
- 临界区竞争
- 偶发崩溃

#### C++ 内存管理风险（已修复一项）

哈希表使用的是数组分配：

- `hashtable = new HashNode[HASHTABLESIZE];`

历史版本释放时却写成：

- `delete hashtable;`

本次实现已改为 `delete[]`，该风险已修复。

#### 工程文件可移植性差（已部分修复）

`jqai.vcxproj` 里保留了旧机器上的绝对输出路径，例如 `D:\work\...`。这会导致：

- 新环境构建时路径不正确
- 输出位置不可预测
- 工程迁移成本增大

本次实现已将主要输出目录改为相对路径，并把中间目录统一迁移到 `JQ/_obj`。

#### 依赖老旧（已部分迁移）

- 主程序已迁移到 `.NET Framework 4.8.1`
- C++ 工具集已迁移到 `v143`
- 构建环境已验证为 Visual Studio Build Tools 2022

这会提高新机器复现成本，也限制后续技术升级。

#### 测试体系缺失

虽然仓库里有 `test` 工程，但它不是单元测试项目，而是一个辅助生成程序。当前项目缺少：

- 自动化规则测试
- AI 回归测试
- 局面合法性测试
- 构建后的烟雾测试

#### 文档仍不完整

目前仓库中已经有 AI 讲解和 HTML 摘要，但还没有一份面向维护者的“项目全景说明”，例如：

- 规则摘要
- 构建步骤
- DLL 与主程序关系
- 棋盘编码方式
- 行棋字符串协议说明

本文件正是对这部分空白的补充。

## 10. 当前项目的可维护性结论

如果从“功能是否存在”看，这个项目已经具备完整主干。

如果从“是否适合持续扩展”看，目前它仍处于“研究型原型到工程化产品之间”的阶段，主要原因是：

- AI 很强，但实现高度集中在单个 `ai.cpp`
- UI 与规则逻辑耦合较深
- 线程处理方式偏旧
- 构建和部署依赖本地历史环境
- 缺少自动化测试

因此，这个项目最适合的定位不是“可长期大规模协作的现代工程”，而是“功能完整、算法含量高、但工程化程度中等的研究型桌面项目”。
